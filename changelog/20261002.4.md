## 一、边界决定：代码更新只到 `panel_plan`

**客户定（2026-10-02）**：布局与板件（以及服务这两段的编排：建项目、工作副本与编辑租约、房间确认、决策台账、`stage_input` 通道、`furniture_*` 工具）继续改；**制造 / 特征树 / CAD / 交付即将重写**，不再投功夫。

## 二、CAD 成本量清了，并**否掉**了"一个进程连做几台"

| 项 | 实测 |
| --- | --- |
| 每台一个进程 | **4.2 秒/台**（2 台 9.3 s、3 台 12.4 s） |
| 拆开 | 导入 build123d **2.4 s** + 建模 **0.25–0.7 s** + viewer 导出 **约 1.4 s** |
| 模型脚本自带缓存 | 产物未变时 **0.03 s** 返回，**但进程照样起**（省不掉那 4.2 秒） |
| 一个进程连做几台 | **更慢**：两台柜 **20.1 s vs 9.3 s** |

原因：**viewer 拓扑导出必须待在刚建完模型的那个进程里**——长进程里导出同样三台要 **6.7 秒/台**，在模型自己的进程里只要约 1.4 秒（CAD 内核与网格状态是热的）。所以"把桥的整段配方搬进一个进程"今天不划算；要复活它，前提是**让模型脚本自己产出 viewer 包**（上游 cadgen 的事）。

**代码没留**（试完就撤，不留更慢的死代码），数字与结论记在 [TOOL.md](../domain/skills/cad-generated/TOOL.md) 与[未落地需求](../domain/skills/cad-generated/references/backlog.md)「方向 3」。**下一件是内容寻址复用**，但它整个在下游——按第一节的边界**暂停**。

## 三、拆分求解器：`space → 单元`（批次 1+2）

| 新文件 | 干什么 |
| --- | --- |
| [craft_catalog.py](../domain/skills/layout-plan/scripts/furniture_layout/craft_catalog.py) | 车间工艺目录的**加载与准入**（区间/档位/策略；负数、区间反了、策略不认识、未知键 → 加载时就拒）；**缺项抛 `MissingCraftData`**，消息说清"缺什么、给谁用、往哪加" |
| [space_split.py](../domain/skills/layout-plan/scripts/furniture_layout/space_split.py) | 求解器：净尺寸（扣收口，支持现场值 `filler_mm=`）→ **先定门**（门扇上限 → 单元宽度上限）→ 功能格 → 合规单台；不可行抛 `SpaceInfeasible` 并给可行做法；id 发号 `{space}_u{n}` **只增不复用** |
| `scene.py` 的 `SpaceRequest` | `rooms[].spaces[]` 契约：`id` / `kind`（柜类，词表来自目录）/ `mode` / 墙与起端（或自由坐标）/ 净宽 / 可选深高 / `constraints` / `pinned` |

**目录开始真的驱动行为**：厨房地柜不写高度 → 用目录的"台面完成面 830 − 台面厚 15 = **815**"；衣柜不写高度 → **停问**（目录没有可推的数）。**没有 `spaces` 的老输入连目录都不读，行为逐字节不变。**

**不可行就停问，不再静默变形**：一块 2400 的墙不再变成"2400 宽的假包络"，而是给出"超过两扇门上限 900，且目录还没有标准单元宽档 / 功能格最小净宽"＋两条路。

## 四、页面「空间」卡片 + 修掉"一拖动就丢 spaces"

- 侧栏新增**「空间」卡片**：每块空间一行（柜类 · 靠哪面墙 · 多宽），下面列出它展开出的**单元**（点一下选中），**钉住的单元带"钉住"记号**；「家具」列表里也标出空间单元/钉住。没有空间的房间**收起卡片**（老工程看不到它）。
- **分组是现算的、不存映射**：单元 id 就是 `{space_id}_u{n}`，把前缀对上的件挑出来即可。
- **修掉一个真 bug**：页面一拖动，`spaces` 会被丢掉（`room_scene_source` 只带 `room`+`items`），那一排从此退化成"手工摆的几件家具"。现在空间跟着走。

## 五、移动语义（设计稿 §十一 第 1 件）

| 客户说 | 操作 | 后台 |
| --- | --- | --- |
| "**这一台**宽一点 / 挪一点" | 画布上拖那一台 | 改这台 **＋ 自动写进 `spaces[].pinned`**（手改 = 升格为钉住）；钉住必须在**重解之前**写进源里，否则刚改的那台会被当"旧解"丢掉 |
| "**这块地方**往左挪 / 变宽" | 「空间」卡片里改起点/宽 → 「重解」 | 新 op `{"op":"space","space_id","offset_mm"?,"width_mm"?}`：**没钉住的由空间重解，钉住的原样不动** |
| 钉住的被挤没了 | — | **停问**："你钉住的那台 north_run_u1（200~940）放不进这块地方（200~600）了——放宽到至少 740，或者取消钉住" |

- `plan_scene` 的口径写死成三条：**钉住的照原样 / 没钉住的由空间重解 / 与空间无关的显式件原样留着**（重放幂等）。
- `/layout/edit` 收两类 op；服务端模型校验**身份不含糊**（件级要 `item_id`、空间级要 `space_id`，两个都给会被拒）。
- 只读页（预览/分享）看不到改空间的输入框。

## 六、`fill` 迁移（批次 3）

`fill: true` 的件现在**走求解器**，不再给"一个任意宽的大包络"：

| 场景 | 结果 |
| --- | --- |
| 净宽 ≤ 两扇门上限 | **一台合规单元** `{原id}_u1`，宽度是**净宽**（扣现场收口） |
| 墙太长、目录又没有单元宽档 | **停问**，并指出两条路：缩短空间 / 改用 `spaces[]` 写 `split=equal` 走等分 |
| 没写 `kind`（柜类） | **停问**："这件沿墙铺满的 'wardrobe' 没说要做什么柜……代码不替它猜柜类" |
| 原件 `manufacture: false` | 展开出来的单元**继承**它 |

**`split=equal`（等分）是显式选项，不是默认**：等分是确定性的、也满足硬约束，但它**不是车间要的档位**，所以结果带一条助手假设"宽度还没和车间档位对齐"，余量集中在**远端那一格**。

**行为变化（要记住）**：`fill` 件现在必须写 `kind`；宽墙铺满从"给假包络"变成"停问"；展开后单元 id 从 `wardrobe` 变成 `wardrobe_u1`（老工程用 `fill` 的件重算后 id 会变、板件要重算）。

## 七、成柜方式与移动语义的口径（设计稿 §十一）

**空间**负责"这块地方 + 要什么"；**成柜方式**（`build_as`）负责"做成几台模块还是做成一整台"；**单元**负责"可制造"。

- 客户问得对：**加了中立板，大包络不拆也能出板件**——所以"能不能出板件"不是拆不拆的理由。真正的约束是**门数上限（今天 ≤2）、按台制造与包装、以及中立板今天还没有**。
- 所以拆不拆是**工艺选择**：`modules`（今天唯一可用）/ `one_carcass`（**要板件阶段先支持中立板 + 多门**，属下游重写范围）。成柜方式变了**只改展开器的一支**，空间契约、单元契约、下游五字段、继承判据都不动。

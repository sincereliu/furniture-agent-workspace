# 20261002.3 — 多柜真的能用：下游逐柜、拆脚手架、逐柜参数

接 [20261002.2](20261002.2.md)。这一次把「一格一台柜」从**形状**做到**能到车间**，并顺手把为它让路的兼容层全部拆掉。

一句话验收：**一个两台柜的项目，两台各自一整套产物（BOM / 特征树 / STEP / 钻孔 / 六面钻 XML）都进交付清单；少一台会被拦住。**

## 一、下游逐柜：制造 / 特征树 / CAD / 交付清单

以前下游只读 `cabinets[0]`（主柜），所以拆成三台**只有一台能走到车间**。现在四个阶段全部逐柜：

| 阶段 | 产物形状 | 验收 |
| --- | --- | --- |
| `manufacture_plan` | `{"cabinets": [{"id", "bom"}]}` | 每台按**它自己**的 spec/板件算，问题点名是哪一台 |
| `feature_tree_planned` | `{"cabinets": [{"id", "tree"}]}` | 同上 |
| `cad_generated` | `{"cabinets": [{"id", "bridge"}]}` | 一台柜一个源文件、一份 STEP；失败点名 |
| manifest / 交付 | 柜级记录带 `cabinet_id` | **`MISSING_CABINET_ARTIFACT`**：规划过的每台都要有 `step` / `drilled_holes` / `six_side_drill_xml` |

- 顺序与身份**完全来自布局**（不挑、不排、不漏）；产物形状被压扁成单份**直接拒**（`manufacturing_handoff.cabinets_from_manufacturing()`、`workflow_cabinets.cabinets_from_feature_trees()` / `cabinets_from_bridges()`）。
- 柜级文件按柜名区分：`bom.<cabinet_id>.md`、`<cabinet_id>.step`、`<cabinet_id>.drilled-holes.*`、`六面钻文件/{cabinet_id}__{role}.xml`；阶段级 JSON 仍是每版一份（内容本身已逐柜）。
- 就绪度：柜级记录对**它自己那台**，阶段级记录记**整份工程**（取最弱的那台——一台没定，整份不算定；顺序取自既有的 `MANUFACTURING_READINESS_LABELS`）。
- 旁路分析（生产仿真/试制统计）吃的汇总视图由 `merged_manufacturing_view()` 给：各柜拼接 + 就绪度取最弱，**只读、不写回**。

**成本口径**：桥是**一个源文件起一个进程**，实测约 **5 秒/次**，所以 CAD 阶段是 **N 台 ≈ N × 5 秒**（2 台 ~10 s、3 台 ~15 s、6 台 ~29 s——正好压到 [TOOL.md](../domain/skills/cad-generated/TOOL.md) 里"单次 >30 秒"的唤醒线）。要压只能靠"一个进程连做几台"或"按柜内容寻址复用"，即[未落地需求](../domain/skills/cad-generated/references/backlog.md) 的「方向 3」。

## 二、拆脚手架：不给旧 CAD 留兼容

原则（客户明确要求）：**下游还要改，就不能为它保留兼容层**。所以这些一次拆干净：

| 拆掉的 | 为什么 |
| --- | --- |
| `Revision.feature_tree`（"主柜那棵"的镜像）+ 序列化键 + 三处赋值 | 同一棵树存两份、可能不同步；CAD 逐柜后它没有存在理由 |
| `primary_feature_tree()`、`primary_bom()`、`_spec_from_revision()` / `_structure_from_revision()` / `_placements_from_revision()` / `_panels_from_revision()` / `_bom_from_revision()` | 清一色"只读主柜"的旧入口 |
| `require_primary_handoff()`、`primary_cabinet()` | 默默取第一台——多柜工程里会算错对象 |
| `OrchestrationResult.pipeline` / `.bridge` / `.drilled_holes`（单数） | 换成 `cabinets` / `bridges` 两个**逐柜元组** |

**"只看一台"现在有了说清对象的写法**：`panel_planning.cabinet_identity.cabinet_handoff(output, cabinet_id)`——哪一台必须由调用方写明，没有"默认第一台"这个入口了。

## 三、逐柜参数：设定跟着各自的柜

`stage_inputs.panels` = **一份共享提案 + 按柜覆盖**：

```json
{"parameters": {…所有柜的底…}, "cabinets": {"cabinet_2": {…这台要覆盖的字段…}}}
```

- 覆盖是**逐字段**的（`{**共享, **这台}`），合起来必须是一份完整合法的提案——不合法的结果照旧由阶段验收拒（不替人补默认值）。
- **身份与几何不许覆盖**（`cabinet_id` / 柜类 / 宽深高只来自包络）；**陌生柜名直接拒**（不静默忽略）。
- 制造选项同样逐柜：`manufacturing.cabinets[柜名]` 覆盖 `parameters` 与 `appearance`。
  **这条是被实测逼出来的**：把第二台改成单门后，制造阶段报 `door_hinge_side must be 'left' or 'right' for a single door`——共享一份铰链方向根本表达不了"一台双门、一台单门"。
- `revise_stage_output(panel_plan)` 改成把**每台自己的 spec 写回它自己的覆盖**（旧做法是把第一台的抄给全部柜，测试已钉住这条回归）。
- 平铺写法：`stage_inputs_from_spec` 接受 `panel_cabinets` / `manufacturing_cabinets`。

## 四、旁路分析也要指名（审计与择优不是互斥，是两个轴）

| | 范围 | 产出 |
| --- | --- | --- |
| `panel_unit_audit` | 默认**逐台**（`config.cabinet_id` 可只审一台） | 逐台明细 + 合计；问题条目带 `cabinet_id` |
| `panel_optimization` | **必须指名**（多柜不指就报错） | 候选自带 `cabinet_id`，**落地只改那一台**，其余柜不动 |

顺手修了候选复核口径：候选摘要记的是**它那台柜**那份产物（以前是整份），否则逐柜落地会被误判成"不可复现"。

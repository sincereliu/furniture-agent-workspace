# 页面写项目（设计稿）

这一页说清「页面上拖一件家具，项目里到底发生了什么」。契约细节见
[运行时契约](runtime-contract.md)「页面写项目」段；待评审与已知缺口登记在
[编排与生命周期未落地需求](backlog.md)；修订继承见 [修订继承设计](revision-inheritance-design.md)。

## 分水岭：页面能写项目了

在此之前，写项目只有一条路——对话（`furniture_revise_layout`）或确认流程；页面是**只读投影**。
现在多了一条：页面上改一件的摆放，**落成一个新 Revision**。

这是有意的：只读页能看不能改，用户每改一厘米都要回来找助手，反馈环太长。但"能写"必须付代价，
所以三条约束同时成立——**一次只改一件**（原子）、**必须带版本**（不许拿旧画面覆盖）、
**默认关闭**（灰度开关，没验证过就不开）。

## 为什么是「每次一个新 Revision」

- Revision 是这条流水线的审计单位：**历史不改写**。原地改最新 Revision 会让"已经确认过的内容"
  悄悄变样，`layout_sha256` 与冻结文件、下游 attempt 的血缘全跟着含糊。
- `revise()` 本来就干这件事：下游全部作废、父修订产物标 stale。页面改摆放与对话改摆放**是同一件事**，
  不该有第二套语义。
- 代价要认：连拖 20 次就是 20 个 Revision。真要治，方向是**同一次会话内的合并**
  （在最新 Revision 还没确认、还没有任何下游输出时原地改），属于后面的事，先不做——
  它会把"历史不改写"这条规则变复杂，得先有真实使用数据说明值得。

## 为什么改完就变成「未确认」

确认位是**人对某份内容点过头**的记号（`approved_stages` 的语义同此，见修订继承设计）。
改过的内容没人点头，所以被改动的那一间**退回待审**：

- 不继承确认位 = 不伪造审批。审计时"这一版是谁什么时候点头的"必须答得出来。
- 冻结文件只写已确认布局（`JsonProjectStore._write_frozen_layout`），所以确认一撤回，`layouts/` 里那份就不再对应本版内容——下游想读也只能先重新确认。

### 房间级确认（已落地）：改一间只审一间
"整份布局重新确认一遍"这个代价太大——改次卧的床头柜不该让主卧重新审。所以确认粒度下沉到房间，
但**下游的闸门没变**：`layout.confirmed` 仍是唯一开关（panel / 制造 / CAD 的契约一个字没改），
它是"每间都审过"的**派生值**：

- `Revision.approved_rooms` 记"人看过哪几间"；`confirm_room(project, room_id)` 审一间，
  `pending_room_ids()` 说还差哪几间；全审齐时布局才 `confirmed` 并进 `approved_stages`。
- `confirm_stage(layout_plan)` 保留"一次确认全部"的老语义（等价于把剩下的房间一次审完）——
  工具面、老流程、老测试都不用改。
- **没动过的房间，确认跟着走**：新 Revision 里某间房的内容与父修订**逐字节相同**且父修订审过它，
  就自动记入 `approved_rooms`，并在 `inherited_rooms[room_id] = {sha256, from_revision}` 留痕
  （R2 的同一条规矩：沿用要回指到真正点头的那一版）。若这样凑齐每一间，布局检查点当场成立。
- 老项目文件没有 `approved_rooms`：那时 `confirmed: true` 是唯一记号，等价于"每间都审过"。

于是两种改动的代价分开了：**改一间 → 只审那一间**；**一间都没动（例如只改了 `stage_inputs`）→
一间都不用审**。"改动落在哪一间"的判据是逐字节比较，不看人的描述。

## 编辑租约（已落地）：同一时刻只有一个写者

写权限（`may_edit`）回答"这台机器上能不能写"，租约回答"**此刻轮到谁写**"。页面拖动与助手改布局
都能动同一个项目，`expected_version` 只能事后发现（409），租约事前就分开。

它落在 `<store>/<project-id>/edit-lease.json`（tmp + replace 原子写）——**因为写者不在同一个进程里**：
页面走 HTTP 服务进程，助手直接在另一个进程里调 orchestrator，内存里的锁互相看不见。

三条规矩与两个刻意的取舍：

- **有 TTL（45 秒）**：页面每 5 秒心跳续租，助手每步续一次；关标签页、崩溃、断网都不用管。
  没有 TTL 的锁会把一个开着的标签页变成"永久占位"。
- **不静默接管**：被别人持有就是 `LeaseHeld`，接口回 **423**（带 `holder` / `label` / `expires_in`）。
  人把活交给助手 = 授权让出（方案 B），由 `handover_to_agent()` 显式转移，工具面在**写动作之前**
  自动做这件事，并在结果里回一句 `handover.message` 让助手转告人"页面已切成只读"。
- **人永远抢得回来**：`transfer()` 原子的，页面的「收回编辑权」按钮走 `/edit-lease/takeover`。
  收回之后助手的下一次写会拿到 423 并停下——**租约不是用来把主人关在门外的**。

看得见：页面每秒轮询的布局文档里带 `lease` 快照（`holder` / `label` / `expires_in`，**不含 token**），
所以"助手正在处理 · 44 秒后自动释放"不需要多发一个请求；租约变化与版本无关，`pollLayout` 在比对版本
之前先应用它。`id` 是公开的（页面据此分辨"那个 page 就是我"还是"另一个窗口"），`token` 是秘密
（写请求用 `X-Edit-Lease` 带回，页面存在 `sessionStorage`）。

**页面这一侧（P5 的范围）只做"看得见"与"抢回来"**：预览页今天仍是只读，所以它不申请租约；
自己申请、心跳、闲置让出、以及"能不能拖"是下一步（页面接入）的事。

## 工作副本（方案 H，已落地）：边界是下游产物，不是时间

一次摆放不是一次手势：放下 → 看 → 挪一点 → 再看 → 量个尺寸 → 回来再挪。这一整段是**一个意图**，
不该变成十个版本。所以最新版在"还没有下游产物"期间就是**工作副本**：

| | 还没有下游产物 | 已经有下游产物 |
| --- | --- | --- |
| 改动的落点 | **原地改这一版**（版号不变、内容摘要变） | **追加新 Revision** |
| 为什么 | 还没有东西依赖它，改多少次都还是同一个意图 | 已经有东西依赖它了，再改就不是同一版 |
| 撤销日志 | 每次改动记一条（改动前的旧值） | 新一版从空日志开始 |
| 被改房间的确认 | 退回待审（拿掉 `approved_rooms` 里那一条；不再全审齐就撤回确认位） | 同左（新版里那一间待审，其余沿用） |

**撤销跟着"有没有人依赖它"走，不跟着钟表走**——这是刻意的选择。时间只是"还有人看着吗"的代理指标，
而下游产物是直接指标：没有下游产物时摆一小时也能撤，有了以后十秒也不能撤（那时往回走是"修订"的事：
明确、留痕、下游跟着作废）。

日志的几条细节：

- **记"改动前的旧值"，不记"从头重放"**。所以丢最旧的几条只意味着"撤不到那么远"，不会让撤销错位
  （上限 `WORKING_OP_LIMIT=500`，超出丢最旧）。
- **日志不是审计**：下游一产出就清空（`Revision.close_working_copy()` + 一条事件）。审计靠 `workflow`
  事件行——"这一版里发生过 8 次调整""撤销过 2 步"看得见，但每一步的细节不留。
- **撤销留痕**：它会改掉"已经跟人说过"的内容，所以必须记一条 `undo N step(s)`。

**人看得见**：页面常驻一块牌子——「草稿中 · 同一版 · 已调整 N 次」或「这一版已有下游产物：改动会落成
新一版」。`version`（内容摘要）原地改也会变，所以别的窗口和助手照样能察觉（这是方案 H 能成立的前提）。

## op 与几何：复用，不重写

op 词表、字段白名单、墙摆/自由摆放的互斥规则全部复用房间场景编辑（`scene_edit.apply_edit`）。
项目布局里每一间房本来就是一份 `RoomScene`，把它还原成"场景源"（`project_edit.room_scene_source`）就
能直接喂给同一个应用器——**不引入第二套字段判断**，也就不会出现"场景页允许、项目页拒绝"这种漂移。

改完必须重算：`plan_scene()` 重新摆放 + 准入校验，`footprint` / `clearances_mm` 是算出来的，
所以权威数据（`placement`）改了、派生数据不会留着上一版。校验不过就整体拒绝。

**`fill` 件是例外**：它的宽与偏移由墙上的空段反推（`placement.fill_span`），改完就被覆盖。
所以对 fill 件的摆放类 op 一律 422 说清原因——静默接受再丢掉是最坏的一种"成功"。
（改房间尺寸导致 fill 件变宽，那是房间编辑的事，不是摆放编辑。）

## 架构位置

HTTP 层不自己开 orchestrator（`test_entrypoint_architecture` 钉着这条）。页面写项目走
`furniture_workflow/project_layout_edit.py` 这个门面：它校验开关与版本、调
`furniture_layout/project_edit.py` 算几何、再驱动 orchestrator 造 Revision 并落盘。
几何在 layout 包、版本与生命周期在 workflow 包，两边都能单独测。

## 页面接入（已落地）

- **能不能编辑由服务端按权限渲染**：本机来源（`may_edit`）给可编辑页，其余给只读页；
  `?mode=view`（分享形态）在本机也强制只读。**URL 参数不是权限**——参数谁都能改。
- 可编辑页还要自己拿到**编辑租约**才算真的能写：进页面申请、5 秒心跳、**闲置 5 分钟自动让出**
  （点一下就能拿回来）、离开页面归还；助手持有时显示「助手正在处理」+「收回编辑权」。
- 拖动 → `POST /layout/edit`（带 `expected_version` 与 `X-Edit-Lease`）；失败按原因说清：
  **423** 助手正在处理 · **409** 画面过期（区分"内容被改了"与"刚被确认"）· **403** 没有写权限 ·
  **422** 这次改动本身不合法。
- 页眉三块牌子：身份的（可编辑 / 只读预览 / 只读分享）、**工作副本的**（草稿中 · 同一版 · 已调整 N 次）、
  编辑权的（你在编辑 / 助手正在处理 / 另一窗口）。

## 还没做（各自有归属）

- **撤销按钮**：接口（`POST /layout/undo`）与日志都已就位并有测试，页面暂不放按钮——先按真实使用看要不要露出来。
- **外部只读分享**：见 [访问模式与外网分享](preview-access-design.md)（token 形态，尚未实现）。
- **多窗口编辑**：租约已经保证同一时刻一个写者，但"另一窗口在编辑"的提示还没在页面上做细。

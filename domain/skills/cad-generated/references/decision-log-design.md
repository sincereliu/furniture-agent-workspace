# 决策台账（设计）

回答"这句话是谁说的、我们把它落成了什么、他点头了没有？"；也给页面和交付一个可查的依据清单。

**为什么要有它**：`layout_plan` 里记的是**结果**（房间、包络、摆放），`working_ops` 记的是**改了什么**
（旧值 + 谁改的）。两处都答不出"为什么要这样"。客户说一句"这面墙做满，能装就行"，
落到项目里只剩下几个毫米数——三天后没人分得清哪一格是客户要的、哪一格是助手替他定的。
而下游一切（板件、加工、交付）都建立在这些决定上。

**今天缺的是什么**：原话只活在对话里。工具面收的是结构化字段，项目文件里没有一句话的出处；
页面上的改动虽然进了日志，也只知道"有人拖了"。所以这一步先把**账**建起来。

## 存在哪

项目文件里一份追加式清单：`store/<project-id>/project.json` → `decisions[]`（`Project.decisions`）。

- 挂在**项目**上，不挂在修订上：一句"客户说要通顶"不会因为换了版号就失效，跨修订仍然要读得到。
- 一条都不删。改主意是**加一条**，并把被改的那几条写进 `targets`；旧的一条一个字不动。
- 形状、枚举与引用完整性由 `furniture_workflow/workflow_decisions.py` 一条路把关
  （`admit_decisions()` 校验 + `append_decisions()` 发号），调用方不得自己拼条目。

## 一条记录长什么样

| 字段 | 含义 | 规则 |
| --- | --- | --- |
| `id` | 台账内的号，`dec_1` 起 | 运行时发，调用方给不了 |
| `at` | 记下的时刻（UTC） | 运行时发，调用方给不了 |
| `revision_number` | 记在哪一版上 | 运行时发 |
| `utterance` | **原话**（不加工） | `customer` / `relay` 从**对话**里来的**必填**；助手自己的假设、以及页面上按的按钮（`source=page`，本来就没有话）可以没有——硬要一句只会逼出编造的引语 |
| `interpretation` | 我们把它落成了什么 | 必填 |
| `speaker` | 谁说的：`customer` / `relay`（别人转达的客户话）/ `agent` | 缺省 `agent` |
| `status` | 这条此刻算不算数：`assumption` / `confirmed` / `withdrawn` | 缺省 `assumption` |
| `source` | 从哪来的：`tool`（对话里说的）/ `page`（客户在页面上按的按钮） | 缺省 `tool`；页面那条由服务端写死措辞 |
| `targets` | 这条说法在确认或撤回哪几条（id 列表） | 只能指已存在的条目 |
| `applies_to` | 它落在哪些对象上（房间 / 家具 / 空间 / 格），自由引用 | 形状校验；存在性校验等约束词表落地时再加 |
| `actor` | **谁记的/谁按的**（持锁者 + 标签 + 租约 id） | 只由运行时写，调用方填不了 |

## 三条规矩，都是为了防止"助手替他说话"变成事实

1. **不冒充客户**：缺省 `speaker=agent`。要标成客户说的，必须显式写 `speaker=customer`；
   转达的写 `relay`——它不是客户本人，出错时要分得清是哪一种。
2. **不冒充已确认**：缺省 `status=assumption`。而且**只有 `customer` / `relay` 能写 `confirmed`**，
   助手不能自己点头（模型自己想当然的默认值，永远挂着"助手假设"）。
3. **确认是动作，不是状态**：`status=confirmed` 的条目用 `targets` 指回它确认的那几条，
   而不是去改别人的字段。一次调用里的新说法**不能互相指向**——先记说法，客户后来点头是下一次调用的事。

## "此刻算不算数"是算出来的

台账里的条目一个字都不动，当前状态按顺序派生（`decision_states()`）：

- 后续条目里**最后一条**指向它的 `confirmed` / `withdrawn` 说了算；
- 没人指向它，就是它自己写的那一档。

于是"还差哪几条要问客户"就是 `pending_decisions`（派生态为 `assumption` 的那些）——
工具面快照和页面牌子都读它。历史永远读得出原样，回放任何一版都能重建当时的账。

## 谁写

| 来源 | 谁记 | 怎么保证不漏 |
| --- | --- | --- |
| 客户**在页面上动手**（拖动、改尺寸） | 服务端自动记进 `working_ops`，带 `actor`（当时持锁的人 + 标签 + 租约 id；读不出就写 `unknown`，**不猜**） | 写入口只有一处，顺手就记 |
| 客户**在页面上按按钮**（确认 / 划掉一条假设） | `POST /api/project/{id}/decisions` → `edit_project_decisions()`：措辞由服务端写死（`source=page`），页面只递"动作 + 目标" | 同上；**只能动还待确认的那一条**，已经定过的不再接受表态 |
| 客户**在对话里说话**（要改布局） | 助手在 `furniture_create_project` / `furniture_revise_layout` 的 `decisions` 里带着走 | 校验在动项目之前 |
| 客户**在对话里说话**（但还不用改布局） | `furniture_record_decision`：只追加台账，不动布局、不动阶段（`progressed=false`） | 同上 |
| 客户点确认 | 记一条 `speaker=customer, status=confirmed, targets=[…]` | 页面按钮或助手记录，两条路都落到同一条规矩上 |

写动作的准入顺序是硬的：**先 `admit_decisions()` 校验，再动项目**——说法不合法就整批拒绝，
不留一个开了一半的工程或一个新版。

## 看得见

- 工具面快照：`decisions`（全量）+ `pending_decisions`（待确认的 id）。
- 项目页：牌子「助手假设 N 条 · 待确认」**可以点开**——每条显示"原话 → 落点"，可编辑页上
  每条配「确认 / 划掉」两个按钮；只读页只显示、不给按钮（并说明为什么）。
- 「已调整 N 次」那块牌子的**悬停**能看到最近三次改动：时间 · 谁（页面窗口 / 助手 / 不知道谁）· 改了什么。
- 交付：还没做——未确认的假设应该跟着板件清单/交付清单一起列出来。

## 还没做（留给后面）

1. **动作与台账不一致时自动作废**（2026-10-02 客户实测撞到）：客户手动拖过某一台之后，台账里针对**同一处**的待确认假设仍挂着"待确认"（实测：假设写"沿墙 300 居中"，柜子已经在 340，两边打架，直到人手动划掉）。
   要做的口径：**动作是最强证据**——
   - 假设记清"它定了哪一处的什么"（`applies_to` 从对象级细化到 `对象.字段`，如 `cabinet-1.offset_mm`）；
   - 布局写入改了那个字段 → **自动追加一条作废**（`source=page`、`actor`=当时持锁者、`targets=[那条]`、`interpretation` 写明"客户直接把 X 改成 Y，与这条不一致"）；
   - **只对"还待确认的助手假设"生效**：客户已经点头过的约束不自动作废，那要显式改并问一句；
   - 页面上"被动作动摇"的标出来（自动作废落地前，至少先让人看见）。
2. **`applies_to` 的存在性校验**：现在只校验形状；等"空间 / 格"这套词表落地后要能核对到真实对象。
3. **"没有依据不许写"的闸门**：凡是有语义选择的字段（分几格、几扇门、通顶与否），要么能指到一条 decision，要么显式标成助手假设——需要先有约束词表（拆分器那一步）。
4. **交付清单列出未确认假设**：`delivery_validated` 的清单里带一段"这几条是助手替你定的"。

# LLM 与运行时边界

适用于创建、修改和审查 `domain/stages/` 下家具阶段包、独立模块 `domain/modules/ai/` 与 `domain/modules/web/`、CAD 执行工具、家具工作流入口、路由 Skill 及其测试。本文的运行时代码同时包括阶段 `scripts/` 与独立模块中的实现。

本文规定 LLM/代码分工与正式文件准入。阶段字段、工具调用及合法值以各 Skill 和现行契约为准；路径范围、同步和维护要求见 [仓库约定](../../../../AGENTS.md)。

确定性执行理由只是分工依据；进入正式文件还须通过下述完成度准入。

## 总原则

**LLM 提案，代码准入。**

- LLM 理解开放语言、提出草稿、解释假设，并把可选择结果交给用户确认。
- 代码只接收规范化结构，保证可执行性、一致性和失败安全。
- “代码可实现”不是把逻辑放入代码的理由；只有确定性执行需求才是理由。

## 正式文件准入

正式运行时代码、当前 Skill/TOOL 和现行契约只提供、描述已经可用的能力。未完成方案留在 `backlog/`，未完成实现留在开发分支或隔离工作区。

- **按可用行为划分交付。** 开始前明确验收条件；每期须独立可用。「字段/枚举/角色表先接入，几何、消费者或交接以后再做」不算完成一期。
- **不预埋未来机制。** 不提前加入未实现能力的字段、枚举、默认值、映射、分支、解析器、注册表、开关或兼容补值。只有测试/mock 调用、没有真实执行路径的机制也不进入正式代码。现行契约需要的拒绝校验可以保留，但不能借此搭建未来接口与角色体系。
- **验证真实执行链。** 按能力实际范围检查入口、产物及适用的保存/读取、交接和校验；schema、件数表或 mock 验收不能代替真实产物与消费者。被开关关闭、被准入拦住、旧产物不变、测试全绿，都不能代替完成度验收。
- **契约只写当前能力。** 不提前列入未来字段、组合和公式；未实现设计、分期、待定参数放在待办，Skill/TOOL 可链接并说明当前不支持。已实现能力的限制和校准状态照实记录。不受支持的输入明确拒绝，不用丢字段、补默认或兼容回退掩盖缺口。
- **交付前审查并报告。** 提交、合并、推送前检查新增能力是否闭环、正式路径有无预备机制，报告支持范围与证据。提交名中的「未完」只是线索，按实际行为判断；审查规则不等于自动拦截，不新增靠关键词、注释、命名或固定文案判断完成度的门禁。

## 谁做什么

执行者只有两个：LLM 和运行时代码。Skill 与 `references/` 不是第三个工人，只是把 LLM 要用的判断标准写在哪。

LLM 做：

- 同义表达、语义分类、上下文消歧和置信不足时的追问。
- 审美、用途、偏好等开放判断，以及多个合理候选之间的推荐。
- 把用户叙述整理为阶段草稿。阶段技能或目录已经写明的默认值或省略后展开（工艺卡料档、省略的层板净高和踢脚支撑数、封边 ABS 1.0mm）按该口径提交，不必再问。没有点名默认、且会改变结果的开放选择，标成待确认假设，一次列出。
- 面向用户的解释、假设展示和下一步问题选择。
- 旁路分析里选目标、读候选、决定要不要采纳。

运行时代码做：

- 规范字段、Schema、允许的规范枚举和阶段字段所有权。
- 数值、单位、几何、公差、碰撞、数量关系和制造不变量。
- 阶段状态、确认、Revision、谱系、持久化和下游失效。
- CAD、BOM、文件、API 等确定性转换或有副作用的操作。
- 不经过 LLM 的结构化 CLI/API 契约；只接受已规范化值。
- 旁路分析的确定性计算或引擎调用。结果写入 `stage_analyses`，是证据不是阶段事实，不得直接覆盖 `stage_outputs`。用户选中候选后，按字段所有者走 `revise()` 或 `revise_stage_output()`。

写进所属 Skill 或 `references/`，不要写进运行时代码：

- LLM 做判断所需的领域口径、非穷举语义示例和追问标准。
- 阶段边界、用户可见检查点、何时停止以及何时需要确认。
- 说明性目录可以列规范值和语义示例，但运行时代码不得把示例变成别名或关键词匹配器。

## 写代码前的判定

对每个准备新增的函数、分支、映射表、默认值或解析器依次检查：

1. 它是否直接解释自然语言、关键词、同义词或模糊偏好？是则默认归 LLM。
2. 它是否只是从多个合理方案中选一个，而且用户能在执行前确认？是则归 LLM 提案。
3. 相同的规范化输入是否必须稳定地产生相同结果？是则可以归代码；进入正式文件前仍须通过完成度准入。
4. 判断错误是否会造成非法状态、错误几何、加工/BOM 错误或外部副作用？是则必须由代码兜底。
5. 裸 CLI/API 是否必须在没有 LLM 时执行？是则代码只实现并验证明确的结构化协议，不补做自然语言理解。

无法明确回答第 3、4 或 5 项的运行时逻辑，不新增到运行时代码；把决策标准写入所属 Skill。

## 默认禁止的运行时实现

- 自然语言别名、同义词、关键词或正则分类表。
- 用字符串包含、模糊评分或启发式规则猜测用户意图。
- 在代码里决定追问话术、审美偏好或开放方案优先级。
- 在上游阶段静默物化下游默认值。
- 为一个 LLM 可直接完成的一次性判断增加加载器、注册表或框架。
- 把旁路分析结果直接写进 `stage_outputs`。

已批准的结构化协议例外（细节在所属 Skill，这里只点名以免审计误删）：

- 车间工艺卡：提案可省略料档字段，由目录展开为具体毫米。这不是按柜型猜方案，也不是解释「厚一点」。
- 层板净高与踢脚支撑数：提案可省略，由板件代码按该柜外形尺寸展开为具体毫米和整数。显式写出的净高和支撑数保持原值。这不是按柜型猜方案。
- 交互协议、`furniture_*` 工具和已保存的项目都使用规范字段名。加载时不把历史字段名恢复成规范名。

其他例外同样必须在所属 Skill 中说明输入契约、停止条件和不用 LLM 的原因，并用行为测试覆盖。

## 完成前边界审计

1. 查看本次差异：`domain/stages/` 下阶段包、`domain/modules/ai/`、`domain/modules/web/`、`cad-generated` 工作流、以及 `.agents/skills/furniture-agent/`。列出新增或扩大的分支、映射、默认值和解析器。
2. 给每项标注一个代码理由：`schema`、`validation`、`calculation`、`state`、`side_effect` 或 `structured_protocol`。旁路分析标 `calculation` 或 `structured_protocol`，并确认只写入 `stage_analyses`。
3. 没有上述理由的逻辑不进入运行时。LLM 已在使用的判断标准写回所属 Skill、`TOOL.md` 或 `references/`；未完成能力的设计与分期写入 `backlog/`。
4. 对有代码理由的新增机制，按「正式文件准入」核对完成度，记录真实执行与消费者的验证证据。
5. 检查代码中是否出现自然语言示例的复制、把同义词当分类器，或上游阶段静默做下游决策。工艺卡展开若已在所属 Skill 说明，不算违规。
6. 测试客观行为与不变量，不测试提示词的固定措辞，也不靠关键词或固定文案自动判定完成度。
7. 交付时在对话中简要报告：LLM 负责什么、代码保留什么、是否存在例外，以及本次已闭环的能力和验证证据。更新日志是否写入以仓库 `AGENTS.md` 为准；这次边界审计本身不写更新日志。

自动化测试只能检查算得对不对、状态对不对、以及这份规则文件还在不在。它不能判断一段逻辑该归 LLM 还是归代码；不要靠在代码里搜关键词代替自己看。改完后仍须做上面的边界审计。
